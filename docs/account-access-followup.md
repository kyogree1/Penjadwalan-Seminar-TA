# Secure account first-access follow-up

## Delivered contract

New guest routes: GET/POST `/forgot-password` (`password.request`, `password.email`), GET `/reset-password/{token}` (`password.reset`), POST `/reset-password` (`password.update`). Login now links to first access / forgot password. Both forms are actual Vue SFCs with processing guards, errors, accessible labels and navigation. Completion clears password fields on finish and displays success on login; it never logs the user in automatically.

Existing randomly provisioned accounts can request first access using their registered email. Possession of the delivered token proves access to that mailbox; it does not establish institutional identity or authorization to change the stored address. A successful completion stamps an unset email verification timestamp, hashes the new password, rotates the remember token, removes that user's persisted session rows using the configured session connection/table, invalidates the current guest session and consumes the broker token. Other users are not modified. No privileged invitation endpoint or automatic create/import mail was added. The existing Tendik predictable-default reset is unchanged and is NOT recommended for onboarding.

Laravel's users broker retains its configured 60-minute expiry and 60-second per-account issuance throttle. Request POST additionally limits callers to five requests per minute; completion POST to ten per minute. Known, unknown and broker-throttled emails receive the same success text. Invalid, expired, wrong-email and replayed tokens receive the same completion error. Passwords require confirmation, at least twelve characters, mixed case, a number and a symbol. Validation failures do not flash tokens, passwords or confirmations. Token URLs are only delivered in the mail and to the completion page; no plaintext secret is returned in flash, CLI output or application logging. Completion pages set no-store/private and no-referrer headers.

The custom notification binds links to configured `APP_URL`, not a request Host header. The request action refuses log/failover/array mailers outside the isolated test exception: allowlisted delivery mailers are smtp, ses, ses-v2, postmark, resend and mailgun. An unsupported mailer produces the same public response but no token/message. This is intentional fail-closed behavior; operators must establish supported delivery before advertising access. Never select a log transport under an allowed delivery name.

## Reset race and delivery failure repair

- Independently reproduced RED: the former transaction-wrapped broker allowed two Fibers to validate the same token and both redirect to login; the failing assertion observed the first redirect still containing `/login`. The repair uses `AtomicPasswordReset`: broker user lookup and expiry/hash checks remain authoritative, followed by a conditional DELETE matching email, stored hash and creation time. Exactly one affected row grants permission to mutate the password. The claim and password/session writes are enclosed in the transaction; an exception rolls back the claim. An unlocked SELECT plus transaction alone is explicitly not treated as a lock.
- SQLite supports this claim through its serialized writer/atomic DELETE semantics, without unsupported `FOR UPDATE`. The regression suspends after the broker token SELECT has returned its stale row; a second completion wins, and the resumed contender cannot overwrite its password. Replay, expiry and password-strength coverage remain green. This is deterministic same-connection interleaving coverage, not multi-process load evidence. Busy/lock errors can still fail a contender without granting a second successful reset; no application lock-retry guarantee is made.
- The bounded deployment contract uses the database token repository, a unique email token row, and the same transactional connection for token and User persistence. Other engines require transactional tables and verified affected-row/isolation behavior; cache repositories, nontransactional engines, split User/token connections, separate session connections and production concurrency/availability testing are not certified. Cross-connection session deletion cannot be rolled back atomically with password changes. Do not replace this claim with a bare broker transaction.
- Notification-failure RED: registered email returned 500 rather than the generic redirect. GREEN: known/unknown/failure responses share redirect and success text; cleanup removes only the matching undelivered token snapshot and permits immediate retry. A replacement created during notification failure survives cleanup. No transport exception is reported or logged by this path, because messages/traces may contain addresses or tokens. SMTP failure can be ambiguous after remote acceptance: cleanup intentionally invalidates that uncertain link and users must request a fresh one. Database cleanup failure remains an operational limitation (the generic response is retained, but retry may remain throttled).
- Fresh verification: targeted backend **10 tests / 82 assertions**, entire backend **188 tests / 2049 assertions**, relevant actual-SFC frontend **3 tests / 10 expectations**, types and production build passed. Targeted Pint passed; build emitted only the existing optional fontaine advisory. Additional replacement-preservation and transaction-rollback tests were added as already-green coverage, not claimed as new RED regressions.
